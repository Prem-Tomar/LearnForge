# Coach key: React and React Native

Use after the learner answers the RQ/NQ prompts in the [web](../tracks/react/README.md) and [mobile](../tracks/react-native/README.md) plans. Require actual state/IDs, a sequence of events, and one fresh variation. Also use [the JS key](javascript-interview-key.md): framework vocabulary must not hide weak language understanding.

## React web

| Question | Expected mechanism and a concrete follow-up |
|---|---|
| RQ01 | A component is a function/type describing UI behavior; an element is a description created for rendering; the browser DOM is the host tree React updates. Calling/rendering a component is not automatically recreating every DOM node. Ask what a changed prop does to the displayed record. |
| RQ02 | Keys identify sibling entities across renders. An index follows position, so removing row A may reuse its component state for B. A stable ID follows the entity. Reorder two edited rows and explain the visible result. |
| RQ03 | Each render receives a state snapshot. Setting state queues a next render; it does not rewrite the current local binding. Two updates based on the same captured count can compute the same next value; functional updates compose against queued prior values. Ask for the result from initial zero. |
| RQ04 | Put shared authoritative state at the nearest appropriate common owner; derive totals from records. A reducer makes named transitions explicit when related updates become complex. It does not make an external source reliable. Ask which state survives switching a workspace and which draft resets. |
| RQ05 | Development Strict Mode can exercise setup/cleanup/setup to reveal broken cleanup; it is not a promise every production effect runs exactly once. Mirror setup with cleanup and use correct dependencies. A save caused by a click belongs in the event flow, not an effect added to hide duplicate runs. Trace subscription counts. |
| RQ06 | Scope by workspace/query/version, assign request ownership, and ignore obsolete completion after change/unmount. Abort saves resources but does not replace ownership checks. Distinguish server cache, hook state and UI draft. Deliver responses backward and observe the result. |
| RQ07 | Client route checks improve navigation, but an attacker can send requests directly. The server authenticates and authorizes each resource/workspace/action. Cookie/CSRF or token-storage choices depend on the actual deployment. Ask for the result of requesting another workspace's ID without the UI. |
| RQ08 | An optimistic view is provisional and needs a predictable reconciliation/rollback policy. For an ambiguous save timeout, use an agreed effect ID and server truth rather than repeating a new effect. Approvals/payments-like actions deserve conservative confirmation. Ask about a second click after timeout. |
| RQ09 | Include workspace/user scope as appropriate, normalized query, filter/sort, page/cursor and relevant data/index/model version. Clear or segregate on identity changes and respect expiry. A key of text alone can mix tenants or versions. Ask how logout affects cached private notes. |
| RQ10 | Transport chunk boundaries do not guarantee message or even decoded character boundaries. Incrementally decode and buffer according to the chosen protocol; parse complete framed events with bounds. A disconnect can leave partial output. Split an event mid-field and ask how reconnection resumes. |
| RQ11 | Approval records consent to a specific current action/version; execution is a durable server operation; UI confirmation reports observed state. A stale button or cached approval cannot override server checks. Ask what happens when the plan changes between display and click. |
| RQ12 | Memoization may avoid repeated work when identity/dependency assumptions hold and the measured cost justifies it. It cannot repair mutation, missing dependencies, wrong ownership, or excessive network work. Profile a concrete slow render before and after a change; correctness must not depend on memoization. |
| RQ13 | A boundary handles errors from rendering/lifecycle of descendants within its coverage; event callbacks, ordinary async callbacks and its own failure need other handling. Check the selected React/runtime behavior for special integrations. A safe version/error display helps diagnosis without exposing private data. Trigger a render error and a rejected request separately. |
| RQ14 | Keep authority and durable actions on the server. Scope cache/request identities, reconcile changes from other tabs, separate drafts from confirmed data, bound retries and show stale/offline status. Walk through two edits with record versions and an uncertain save. Evaluate the learner's explicit conflict policy, not one prescribed library. |

## React Native

| Question | Expected mechanism and a concrete follow-up |
|---|---|
| NQ01 | React reconciles components using native host views such as View/Text, rather than browser DOM elements. Platform layout, accessibility and input behavior differ even when React state principles transfer. Ask why a div/CSS snippet is not directly a native screen. |
| NQ02 | A virtualized list limits active rendered work/window size. Offscreen row components may be unmounted; durable edits belong in explicit feature state/storage, keyed by stable IDs. Measure list size/memory and avoid assuming row-local state always persists. Scroll away and back to an edited item. |
| NQ03 | A keyboard suggests input, but paste, locale formatting, programmatic updates and external data still exist. Text needs deliberate conversion and domain validation; server checks remain mandatory. Compare blank, zero, decimal, negative, and pasted nonnumeric input. |
| NQ04 | Navigation can retain a mounted screen when another is focused. Focus and mount lifetimes differ. Own subscriptions and refreshes according to actual required lifetime, with cleanup; do not trigger mutations merely by navigation. Navigate back after a delayed request. |
| NQ05 | Device localhost addresses the device; laptop binding, firewall, address reachability, certificates and HTTP/HTTPS policy may differ. Diagnose address → transport → status → decoding step by step. Never “fix” a networking issue by disabling authorization or shipping permissive security defaults. |
| NQ06 | Bundled values can be inspected. Provider secrets belong on the backend. Store only the required session credentials through a platform-backed secure-storage adapter with explicit lifecycle; revoke/clear appropriately and redact logs. Ask what logout does after a restart or expiry. |
| NQ07 | Ordinary JS memory disappears on process death. Explicit persisted drafts can survive, subject to OS/user storage lifecycle and migration. Distinguish local pending work from server-confirmed records, handle corrupt/old versions, and minimize private retained data. Kill the process after a draft and inspect recovery. |
| NQ08 | A connectivity signal does not prove the server is reachable, authorized or committed. Use stable action IDs, bounded retries, reconciliation and version-aware conflict handling. Device clocks cannot safely order every distributed write. Walk through two conflicting offline edits and let the user choose a valid resolution. |
| NQ09 | Request only needed permission at a useful point, explain denial, allow cancellation, and provide an alternative/retry/settings path suited to the OS. Validate URI/size/type/lifetime and clean temporary data. Never loop permission prompts or assume a local file URI is remotely accessible. |
| NQ10 | Mobile backgrounding and process death can stop JS execution. The server owns durable agent jobs/checkpoints; the client displays status and resumes with IDs/cursors on foreground/reconnect. A timer is not a reliable job scheduler. Resume after missing several events and inspect durable state. |
| NQ11 | Notification payloads, links and cache entries can be stale or untrusted. Fetch current scoped server state, authenticate/authorize, and bind approval to exact action/version/expiry. A notification tap opens a review flow; it does not authorize execution. Ask about a changed plan after a delayed notification. |
| NQ12 | Measure network start/end, JS computation and render/frame responsiveness separately, using the relevant development/release tools. Development overhead can mislead. Bound data/image/list work and measure a before/after improvement. Ask what evidence distinguishes a slow API from a blocked JS thread. |
| NQ13 | JS-only delivery cannot supply arbitrary missing native code or incompatible native configuration. Runtime/build compatibility, migration, signing and store/platform policy matter. Record the installed build and recovery limits. Test an API-compatible old client; do not promise immediate universal rollback. |
| NQ14 | Persist a bounded local draft/action identity, separate pending from confirmed, restore after restart, reauthenticate if needed, reconcile version conflicts, and retry only within agreed server semantics. UI shows offline/pending/error truthfully. Trace the same action from offline creation through conflict/retry to confirmed server result. |

Record one original answer, one correction if needed, one changed case and the relevant implementation revision. Retain weak questions in future sessions; a learner can accept a code review and still need concept coaching. These guides do not create interview-only or testing-only assignments.
