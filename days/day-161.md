# Day 161: Individual mastery and repair: Capstone performance, cost, and incident recovery

Week 23 · Integrated project and system design · mastery · **240 minutes per developer**

## Goal and real problem

Each developer makes one small behavior repair or improvement in the current capstone performance, cost, and incident recovery increment, explains it, and reviews the partner's separate change.

This is part of **LearnForge**, the same gradually built learning and knowledge platform. The weekly working increment is: Add admission control, useful operational views, and rehearsed recovery for the integrated platform.

## Before starting

- Depends on [Day 160](day-160.md). Both developers need the prerequisite skill, not just a merged PR.
- Review the exact lesson title in the sources below. Use only the session's reading budget.
- Current concepts: Individual mastery and repair: Capstone performance, cost, and incident recovery. Ask the coach to define any unfamiliar word before using it.
- Both people answer today's question independently before discussing answers.

## Session clock

20 recall + 25 Question of the Day/coding + 35 concepts/design + 100 implementation + 30 cross-review + 20 working demo/reflection + 10 break = **240 minutes**.

The implementation block includes a **15-minute individual proof exercise**. The remaining time builds the shared feature. Review and design are learning time, not extra homework. On mastery days, replace most reading with fresh problem solving and a small product repair.

## Explain before coding

A mastery check asks each person to explain and change behavior independently. A small repair keeps this day connected to the working product; the coach selects a fresh edge case, not an unrelated feature.

Explain the idea using a three-value example. Predict the result, run the example, and explain any difference. First choose the simplest correct behavior. Introduce a technical term only after explaining its meaning.

## Concrete behavior and boundaries

Heavy jobs are queued; per-workspace limits hold; model spend is bounded; an incident can be diagnosed and recovered locally.

The team writes down input shape, output shape, invalid-input result, and one failure outcome before implementation. These are internal working agreements, not a request to generate API documentation.

The integration role's product wiring is a thin connection/display step, not a second large feature. Keep the daily slice small enough for the clock.

## System design connected to this task

Set RPO/RTO from user needs, restore dependencies in order, and validate both authoritative data and derived state.

Draw: **caller → today's boundary → state/dependency → result**. Name where invalid input is rejected and who owns state. Walk one failure using the concrete cases above. Compare one simpler alternative with the chosen design. In early weeks, four labeled boxes are enough; later add latency, capacity, consistency, permissions, and cost as relevant.

## Question of the Day

**Your partner reports a failure in capstone performance, cost, and incident recovery. Using this week's concrete cases, how do you locate the first broken boundary, repair it, and explain the design choice?**

Answer in plain English, give an example, then handle these follow-ups:

1. What changes for an empty, invalid, repeated, or interrupted input in today's task? Choose the relevant case and explain why.
2. Which design decision in today's implementation makes that behavior reliable? What does it cost?

Write or speak your first answer before opening the [coach key](../coach/answers-week-23.md#day-161). During cross-review, your partner changes one assumption and asks again.

## Small interview coding drill

**Token bucket:** Trace capacity 5 and refill 1 per second across a burst of 7 requests.

Estimate in-flight requests using throughput times mean service time and discuss tail latency. On day 7 of the week, use a fresh input or a changed constraint. Day 1 traces a small example; day 2 codes a baseline; day 3 improves a structure; day 4 handles an edge case; day 5 explains complexity; day 6 applies it in the project; day 7 solves a fresh variant independently. The drill shares the question/practice time above.

## Pitfall and two-question quiz

**Pitfall:** A team demo or a memorized answer does not prove each person understands the concept. Record individual evidence and hints used.

1. Explain why this pitfall can occur and show a concrete counterexample.
2. Explain the system-design connection above and identify the first boundary you would inspect if today's behavior fails.

The [coach key](../coach/answers-week-23.md#day-161) gives expected reasoning, not a completed production solution.

## Peer review and light checking

Review the partner's implementation. Check the stated behavior, one changed edge case, the design boundary, and clear names. Explain the concept behind a finding and let the owner fix it. The author then explains the updated code. See the [review guide](../TEAM.md).

Use a small runnable example and the existing relevant checks. When today's concept is a testing pattern, inspect or adapt **one short example** with the coach while still shipping the feature. No testing-only assignment, dedicated tester role, coverage quota, or broad regression suite is required. Coach-owned checks may protect important permission, transaction, and effect boundaries.
