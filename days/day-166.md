## Shared concept before personal AI/ML coding

A teach-back asks a learner to explain and change code beyond their usual role. Release readiness requires every owner to understand the complete flow.

Explain the idea using a three-value example. Predict the result, run the example, and explain any difference. First choose the simplest correct behavior. Introduce a technical term only after explaining its meaning.

## Reference behavior and boundaries

All six agree input shape, output shape, invalid-input result, and one failure outcome before implementation. These are internal working agreements, not a request to generate API documentation.

## Step-by-step explanation: behavior and why

Use this actual example: Both explain request-to-effect flow, diagnose a seeded failure, and make a correct small change without copying a solution.

1. **Before:** name the input values, Python types, units, and state before the operation. Predict the observable result.
2. **Checks:** walk the applicable checks in their declared order: representation/shape → local value bounds → trusted identity/scope → business state. Skip checks that do not belong to this unit and explain their actual owner. Reject invalid input before an unauthorized or partial effect.
3. **Mechanism:** trace the calculation, branch, lookup, iteration, await, model/retrieval step, or transition using actual intermediate values. Explain the Python/library/system rule that causes each change; do not just narrate line names.
4. **After:** show the returned/displayed value and any permitted state change. Compare the observed outcome with the stated expectation. Name what remains unchanged.
5. **Failure variation:** change one relevant input or interrupt a dependency. Trace the different path, error, cleanup, cancellation, or recovery and explain why it behaves differently.

The walkthrough explains implementation behavior; it is not an undisclosed extra feature or test-authoring requirement. Use the learner's actual file/line and revision during review. If the learner asks for a fuller explanation, break the mechanism into smaller steps and examples.

## Peer review and light checking

Review the partner's implementation. Check the stated behavior, one changed edge case, the design boundary, and clear names. Explain the concept behind a finding and let the owner fix it. The author then explains the updated code. See the [six-learner review guide](../TEAM.md).

Use a small runnable example and the existing relevant checks. When today's concept is a testing pattern, inspect or adapt **one short example** with the coach while still shipping the feature. No testing-only assignment, dedicated tester role, coverage quota, or broad regression suite is required. Coach-owned checks may protect important permission, transaction, and effect boundaries.

## Implementation acceptance and learning status

Accept a PR when its original owned behavior, agreed contract, relevant failure case, and working integration are correct. Record the revision, checks actually run, and their limits. A pending learning answer alone does not block an otherwise correct implementation, and a later task cannot replace an unimplemented predecessor.

Track concept proof, Question-of-the-Day understanding, shared-architecture explanation, and personal gaps separately in the ledger. Correct implementation may be accepted while conceptual coaching remains pending. If a discussion reveals an actual defect against the original contract, report that defect normally. Do not add learner-written tests or documentation as an undisclosed condition for answering a question. Final interview/mastery readiness still requires individual evidence and repair of weak areas.
