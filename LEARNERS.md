## Review before the next assignment

The peer reviewer or maintainer accepts the original bounded implementation and adds `review-approved`. Close the accepted issue as completed. Only when both review and closure are recorded does the workflow assign the next task. If it is closed before review is recorded, seven upcoming tasks stay prepared but no next task is assigned yet. Adding the review label to the closed predecessor releases the next assignment.

This is implementation review, not a requirement to finish every conceptual follow-up first. Preserve individual Question-of-the-Day understanding and repair separately. A real implementation defect remains a normal review finding.

Roles still rotate; all learn the common concepts and one shared project architecture. If a planned peer has no account or implementation yet, the facilitator records another available peer/maintainer for that review. It does not create a fake learner identity or mark the reserved path complete.

See [ISSUES.md](ISSUES.md) for live queues and [curriculum/cohort.json](curriculum/cohort.json) for the assignment mapping. Current tasks use `queue-current`; prepared tasks use `queue-ready`. No issue is preassigned merely because it is in the seven-task window.
