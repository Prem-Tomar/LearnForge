# React Native: LearnForge on a mobile device

**Optional, unassigned, not yet implemented.** Start with [CLIENT_TRACKS.md](../../CLIENT_TRACKS.md), J01–J14 in [JavaScript](../javascript/README.md), and R01–R06 in [React](../react/README.md). React Native uses React concepts but not a browser DOM. Keep using [the shared JavaScript interview bank](../javascript/INTERVIEW_QUESTIONS.md); mobile interviews also ask language behavior.

Choose an initial device target and framework together at activation. The [official setup guide](https://reactnative.dev/docs/environment-setup) recommends a framework for a new app; consider Expo and record why it meets the product's needs. Record compatible React Native, React, framework, native toolchain, runtime and library versions. Teach the difference between JavaScript source, bundler, native runtime, development build and release artifact. A Windows workstation does not provide a local iOS simulator/build toolchain; record any required macOS/hosted build and actual device access before claiming iOS evidence. An Android-first path is valid, with unverified iOS behavior explicitly recorded.

Default root is `clients/mobile/`. A selected framework may generate extra routing/native files; record their exact integration owner before use. The named feature files below remain the learning boundary. One learner owns one production feature root at a time; other learners use their own isolated exercises for independent concept proof. Do not give two selected mobile collaborators the same screen/function.

For each unit, explain inputs, data owner, result, permission/storage/network side effects, cleanup, failure state and recovery with actual values. The API adapter handles unreliable transport; the feature coordinates visible state; the server validates authority. No SDK/model secret or database access belongs in a mobile component.

## Interview and mastery pattern

Ask the row's NQ question, one earlier JS question, and one fresh device scenario. [The coach key](../../coach/client-interview-key.md) gives expected mechanisms. Use the previous completed session for Question of the Day from N02, and previously learned React/JS material for N01 retention. Keep the original answer and show corrections with a small case.

Every selected learner independently implements native input/layout/navigation, safe networking and sessions, storage/lifecycle, offline reconciliation, permissions, debugging, and a build/install flow. Reviews rotate and include another learner's feature; no person is assigned only platform testing. Collect evidence by named OS/device/build version; simulation is useful but not proof of an untested device or operating system.

Native modules, advanced animation/gesture performance, background services, push delivery infrastructure, on-device ML, and public store release are separate deeper increments when needed. Explain their prerequisites and budget before adding them. A good first implementation does not prove mastery of every native subsystem.

Official references: [React Native introduction](https://reactnative.dev/docs/getting-started), [setup choices](https://reactnative.dev/docs/environment-setup), and [security](https://reactnative.dev/docs/security). The security guide distinguishes server secrets from inspectable application code and discusses platform storage choices. Use current official platform/framework instructions at implementation time.
